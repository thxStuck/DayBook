Что это

Sigma — открытый формат правил обнаружения. Приложение переводит каждое правило в запрос DQL, выполняет его по кейсу и сохраняет результат. Перевод виден в карточке правила, его можно скопировать и выполнить вручную.

Правила в поставке

НаборПравилВерсияЛицензия
SigmaHQ2554 для Windows, 183 для Linuxрелиз r2026-07-01 от 2026-07-09Detection Rule License 1.1
Hayabusa rules196 (Windows)коммит 97b3fd9 от 2026-10-28Detection Rule License 1.1
  • Из SigmaHQ взяты правила rules/windows/** и rules/linux/**, а также правила с product: windows или product: linux из rules/ и rules-emerging-threats/. Из Hayabusa — hayabusa/** (их копии правил SigmaHQ из папки sigma/ не берутся).
  • Вместе с правилами Hayabusa поставляются псевдонимы полей Hayabusa (config/eventkey_alias.txt).
  • К кейсу применяются правила его системы: к Windows-кейсу — правила Windows и Hayabusa, к Linux-кейсу — правила Linux. Сколько правил другой системы пропущено, видно в сведениях о прогоне.
  • Автор каждого правила показывается рядом с каждым срабатыванием. Наборы, версии и полный текст DRL 1.1 — в меню «Правила» → «Наборы правил и лицензии…».

Обновление правил

Кнопка «Обновить Sigma-правила» на экране «Детекты»:

  1. Приложение сверяет установленный набор с последним релизом SigmaHQ и последним коммитом правил Hayabusa на GitHub и показывает обе версии.
  2. Если на GitHub новее — показывает, что будет скачано (архив sigma_all_rules.zip из релиза SigmaHQ и архив правил Hayabusa этого коммита, с размером), и по кнопке «Скачать и установить» скачивает их.
  3. SHA-256 архива SigmaHQ сверяется с опубликованным GitHub; затем собирается новый набор правил, проверяется (правила должны загрузиться, их число — правдоподобным) и только после этого устанавливается в ~/Library/Application Support/<приложение>/Rules/rules.json.
  4. «Запустить детекты заново» — прогон по новым правилам.

Версия каждого набора, дата релиза или коммита и SHA-256 скачанного архива записываются в набор и видны в окне обновления и в «Наборах правил и лицензиях». «Вернуть встроенные правила» удаляет скачанный набор. Если скачанный набор повреждён, используются встроенные правила.

Из командной строки тот же набор собирается командой evtxdump pack-rules <sigma_all_rules.zip> <тег релиза> <hayabusa-rules.zip> <коммит> <rules.json>.

Своя папка правил

  • Меню «Правила» → «Выбрать папку своих правил…». Читаются все файлы .yml и .yaml, включая вложенные папки.
  • Набор называется «Свои: <имя папки>». Изменения в папке подхватываются при следующем прогоне.
  • Отключить — «Не использовать папку «…»».

Запуск

  • Автоматически после импорта, если включена опция «Запустить Sigma-детекты после импорта» (по умолчанию включена).
  • Вручную — кнопка «Запустить детекты» / «Запустить заново» на экране «Детекты».
  • Прогон идёт в фоне. Сначала компилируются все правила, затем подстроки и маски всех правил вычисляются одним проходом по каждому полю (алгоритм Aho–Corasick), затем выполняются сами правила.
  • Результаты сохраняются в кейсе и заменяются при следующем прогоне. «Остановить» сохраняет прежние результаты.

Как правило переводится в запрос

logsource

logsourceСобытия
category: process_creationSysmon 1 и Security 4688
другие категории Sysmon (network_connection, file_event, registry_*, dns_query, image_load и др.)соответствующие события Sysmon
ps_module, ps_script, ps_classic_*PowerShell 4103, 4104, 400/600/800
service: security, system, …журнал по таблице из 42 сервисов

Для варианта Security 4688 поля переименовываются: Image → NewProcessName, ParentImage → ParentProcessName, IntegrityLevel → MandatoryLabel (уровни целостности переводятся в SID S-1-16-…).

Linux (сбор UAC)

logsourceСобытия Linux-кейса
category: process_creationзапуски программ из auditd (Action = process_exec)
service: auditdсобытия audit/audit.log
service: authauth.log, secure и записи journald с facility auth/authpriv
service: syslogsyslog, messages
service: sshd, sudo, cron, clamav, vsftpd, guacamoleзаписи этой программы в любом журнале
только product: linuxвсе события кейса

Поля переименовываются там, где смысл совпадает: в запусках процессов Image → exe, CurrentDirectory → cwd, User → UidName, LogonId → ses; в auditd type → Type, SYSCALL → SyscallName; в sudo USER → TargetUserName. ParentImage и ParentCommandLine в записях auditd нет — правила с ними показывают эти поля как отсутствующие. Категории file_event, network_connection и другие события Sysmon for Linux в сборе UAC не встречаются — такие правила отмечены «не поддерживается» с этой причиной.

Правила с product, отличным от windows и linux, не поддерживаются.

Поля

  • EventID, Channel, Provider_Name, Computer, Level, Keywords и т. п. — системные поля.
  • Остальные имена сопоставляются точно, с учётом регистра.
  • Если поля нет в кейсе, условие по нему ложно, а null — истинно. Такие поля перечислены в карточке правила: «Поля, которых нет в этом кейсе».
  • Псевдонимы Hayabusa (Event.EventData.X и т. п.) применяются только к правилам Hayabusa.

Модификаторы

ПоддерживаютсяНе поддерживаются
contains, startswith, endswith, all, re (флаги i, m, s), cidr, gt, gte, lt, lte, exists, cased, fieldref, base64, base64offset, windash, wide/utf16le (с base64)utf16, utf16be, expand, неизвестные модификаторы
  • * и ? в значениях — маски, \ экранирует *, ? и \.
  • Сравнение без учёта регистра; |cased включает учёт регистра. re учитывает регистр, если не указан флаг i.
  • Ключевые слова (keywords) — подстрока в любом поле.

condition

  • and, or, not, скобки.
  • 1 of … и all of … — по имени, по шаблону с * или them.
  • Условие-список объединяется через or.
  • Не поддерживаются: N of при N ≠ 1, агрегации через | (count() и т. п.), корреляционные и многодокументные правила. timeframe игнорируется.

Если правило не выполнено

Ни одно правило не исчезает молча. В таблице рядом с названием значок, причина — в подсказке и в карточке:

ЗначокЧто значит
⊘ серыйПравило не вычислялось (неподдерживаемый logsource, модификатор, агрегация…)
Красный восьмиугольникОшибка вычисления
Оранжевый треугольникЕсть замечания — например, лимит регулярного выражения

Фильтр «Не вычислены / с замечаниями» собирает все такие правила. По встроенному набору сейчас вычисляются 2734 правила, не поддерживаются 11 (шесть file_access, одно file_rename, три с агрегацией count(), одно без condition), не загружаются 3 корреляционных файла Hayabusa.

Лимит регулярных выражений

На одно значение поля регулярному выражению отводится 2 секунды процессорного времени. Значения, не уложившиеся в лимит, считаются непроверенными, и к правилу добавляется замечание: сколько значений не проверено и по какому полю.

Экран «Детекты»

Панель: фильтр «Сработавшие / Все вычисленные / Не вычислены / с замечаниями / Все правила», минимальный уровень, поиск по названию, автору, тегу, пути или id, меню «Правила», запуск и остановка прогона с прогрессом.

Таблица: Уровень, Правило, Событий, Хостов, Автор, Первое и последнее срабатывание, Набор, Статус. Двойной клик — события правила. Контекстное меню: «События правила», «События правила в таймлайне», «Скопировать DQL правила», «Скопировать запрос событий» (rule = "<id>").

Карточка правила:

  • название, уровень, статус, набор, автор, путь и id, даты создания и изменения;
  • замечания и причины, если есть;
  • «Сработало на N событиях, хостов: M», период, кнопки «События» и «В таймлайне»;
  • описание;
  • «Как проверялось»: logsource, варианты с переименованиями полей, итоговый DQL с кнопками «Выполнить этот DQL» и «Скопировать», время вычисления;
  • теги — техники MITRE ATT&CK ссылками на attack.mitre.org;
  • «Ложные срабатывания (по мнению автора)», ссылки из правила, исходный YAML.

Подвал: время прогона, сколько правил вычислено, не поддерживается, не загружено, с ошибками и замечаниями, сколько сработало и на скольких событиях, длительность.

Где ещё видны срабатывания

  • В деталях события — блок «Сработавшие правила» с уровнем, названием, автором и набором. Клик открывает карточку правила.
  • В боковой панели раздела «События» — уровни правил со счётчиками и ссылка «Все сработавшие правила…».
  • В запросах — поля rule и rulelevel: rule = "<id или название>", rulelevel >= high.
  • Экспорт сработавших правил в CSV — см. Экспорт.

Проверка движка

Команда evtxdump sigma <кейс> --pack rules.json --verify перепроверяет каждое сработавшее правило независимым упрощённым вычислителем, который читает исходное правило напрямую, и сообщает о расхождениях в обе стороны. Это проверка самого движка, а не данных; в приложении её нет.
