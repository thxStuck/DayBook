Принципы

  • Исходные данные только читаются. Журналы открываются только на чтение и отображаются в память только для чтения. База кейса открывается приложением для чтения; писать в неё могут только закладки и результаты детектов, через отдельное подключение.
  • Ничего не скрывается. Восстановленные записи, чанки за заголовком, ошибки контрольных сумм, эвристические связи, неподдерживаемые правила, лимиты и пропуски — всё помечено и объяснено в интерфейсе.
  • Запросы — не SQL. Пользовательский текст никогда не становится SQL-запросом.

Парсер EVTX

  • Файл отображается в память. Формат определяется по сигнатуре ElfFile\0, а не по расширению.
  • Чанки по 64 КиБ независимы, поэтому разбираются параллельно на всех ядрах.
  • Перебираются все физические чанки, а не только перечисленные в заголовке. В «живых» журналах счётчик чанков в заголовке устаревает, и самые свежие события лежат в чанках за ним.
  • У каждого чанка проверяются CRC32 заголовка и данных. Ошибка не останавливает разбор, а помечает записи.
  • Шаблоны BinXML разбираются один раз на чанк и кешируются; вложенный BinXML поддерживается.
  • Поддерживаются все типы значений формата: строки, числа, GUID, SID, FILETIME, SYSTEMTIME, бинарные данные, массивы.
  • Запись с ошибкой разбора не теряется: сохраняется всё прочитанное и ставится флаг.
  • Slack-область чанков просматривается в поисках остатков старых записей (см. Восстановление записей).

Импорт

  1. Параллельный проход по всем чанкам: системные поля, время, место записи; попутно собирается библиотека шаблонов всех файлов.
  2. Восстановление записей из slack с шаблонами всего кейса.
  3. Сортировка по времени. События получают номера в порядке времени, поэтому любой список номеров уже упорядочен по времени. Одинаковые копии объединяются.
  4. Повторный параллельный разбор и запись событий в базу группами по 256 чанков.
  5. Индексы: posting-листы, индексы базы, полнотекстовый индекс, реестр сущностей.

Хранилище кейса

  • Словарь строк. Каждое уникальное значение или имя поля хранится один раз, вместе с хешем строки в нижнем регистре и числовым значением, если строка — число.
  • События. Одна строка на событие: время, системные поля и упакованные пары «поле → значение». Таблица и детали показываются без соединений таблиц.
  • Posting-листы. Для каждой пары «поле = значение» — отсортированный и сжатый список номеров событий. Системные свойства — те же пары с ключами @EventID, @Channel и т. д.
  • Полнотекстовый индекс — триграммный FTS5 по словарю для поиска подстрок.
  • **ts.bin** — время событий подряд; временное окно — двоичный поиск.
  • XML и сырые байты не хранятся: при открытии деталей запись перечитывается из исходного файла по сохранённому месту (чанк и смещение). Номер записи сверяется, чтобы заметить изменённый файл. Исключение — записи с чужим или отсутствующим шаблоном: их XML сохраняется при импорте.

Выполнение запросов

Запрос разбирается в дерево. Каждое условие превращается в множество номеров событий через словарь и posting-листы; and, or, not — пересечение, объединение и разность отсортированных множеств. Подробнее — в разделе DQL.

Детали события

Поля события берутся из кейса и появляются сразу. XML и байты записи читаются из исходного файла отдельно, в фоновом потоке и без блокировки базы: медленный или недоступный файл не тормозит интерфейс. Пока файл читается, вкладки XML и Hex показывают состояние: чтение, «файл не отвечает» (дольше 3 секунд), «не найден», «нет доступа» или «файл изменился после импорта».
