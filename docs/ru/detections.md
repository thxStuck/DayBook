## Что это

[Sigma](https://sigmahq.io) — открытый формат правил обнаружения. Приложение переводит каждое
правило в запрос [DQL](dql.html), выполняет его по кейсу и сохраняет результат. Перевод виден
в карточке правила, его можно скопировать и выполнить вручную.

## Правила в поставке

| Набор | Правил | Версия | Лицензия |
|---|---|---|---|
| [SigmaHQ](https://github.com/SigmaHQ/sigma) | 2554 | Release 2026-07-09, r2026-04-01-50-g552f3fee4 | Detection Rule License 1.1 |
| [Hayabusa rules](https://github.com/Yamato-Security/hayabusa-rules) | 194 | ветка main | Detection Rule License 1.1 |

- Из SigmaHQ взяты правила `rules/windows/**`, а также правила с `product: windows` из `rules/` и
  `rules-emerging-threats/`. Из Hayabusa — `hayabusa/**` (их копии правил SigmaHQ из папки `sigma/`
  не берутся).
- Вместе с правилами Hayabusa поставляются 248 псевдонимов полей Hayabusa.
- Автор каждого правила показывается рядом с каждым срабатыванием. Наборы, версии и полный текст
  DRL 1.1 — в меню «Правила» → «Наборы правил и лицензии…».

### Своя папка правил

- Меню «Правила» → «Выбрать папку своих правил…». Читаются все файлы `.yml` и `.yaml`, включая
  вложенные папки.
- Набор называется «Свои: <имя папки>». Изменения в папке подхватываются при следующем прогоне.
- Отключить — «Не использовать папку «…»».

## Запуск

- Автоматически после импорта, если включена опция «Запустить Sigma-детекты после импорта»
  (по умолчанию включена).
- Вручную — кнопка «Запустить детекты» / «Запустить заново» на экране «Детекты».
- Прогон идёт в фоне. Сначала компилируются все правила, затем подстроки и маски всех правил
  вычисляются одним проходом по каждому полю (алгоритм Aho–Corasick), затем выполняются сами правила.
- Результаты сохраняются в кейсе и заменяются при следующем прогоне. «Остановить» сохраняет
  прежние результаты.

## Как правило переводится в запрос

### logsource

| logsource | События |
|---|---|
| `category: process_creation` | Sysmon 1 **и** Security 4688 |
| другие категории Sysmon (`network_connection`, `file_event`, `registry_*`, `dns_query`, `image_load` и др.) | соответствующие события Sysmon |
| `ps_module`, `ps_script`, `ps_classic_*` | PowerShell 4103, 4104, 400/600/800 |
| `service: security`, `system`, … | журнал по таблице из 42 сервисов |
| только `product: windows` | все журналы; каналы и EventID задаёт само правило |

Для варианта Security 4688 поля переименовываются: `Image` → `NewProcessName`,
`ParentImage` → `ParentProcessName`, `IntegrityLevel` → `MandatoryLabel` (уровни целостности
переводятся в SID `S-1-16-…`).

Правила с `product`, отличным от `windows`, не поддерживаются.

### Поля

- `EventID`, `Channel`, `Provider_Name`, `Computer`, `Level`, `Keywords` и т. п. — системные поля.
- Остальные имена сопоставляются точно, с учётом регистра.
- Если поля нет в кейсе, условие по нему ложно, а `null` — истинно. Такие поля перечислены в
  карточке правила: «Поля, которых нет в этом кейсе».
- Псевдонимы Hayabusa (`Event.EventData.X` и т. п.) применяются только к правилам Hayabusa.

### Модификаторы

| Поддерживаются | Не поддерживаются |
|---|---|
| `contains`, `startswith`, `endswith`, `all`, `re` (флаги `i`, `m`, `s`), `cidr`, `gt`, `gte`, `lt`, `lte`, `exists`, `cased`, `fieldref`, `base64`, `base64offset`, `windash`, `wide`/`utf16le` (с `base64`) | `utf16`, `utf16be`, `expand`, неизвестные модификаторы |

- `*` и `?` в значениях — маски, `\` экранирует `*`, `?` и `\`.
- Сравнение без учёта регистра; `|cased` включает учёт регистра. `re` учитывает регистр, если не
  указан флаг `i`.
- Ключевые слова (keywords) — подстрока в любом поле.

### condition

- `and`, `or`, `not`, скобки.
- `1 of …` и `all of …` — по имени, по шаблону с `*` или `them`.
- Условие-список объединяется через `or`.
- Не поддерживаются: `N of` при N ≠ 1, агрегации через `|` (`count()` и т. п.), корреляционные и
  многодокументные правила. `timeframe` игнорируется.

### Если правило не выполнено

Ни одно правило не исчезает молча. В таблице рядом с названием значок, причина — в подсказке и
в карточке:

| Значок | Что значит |
|---|---|
| ⊘ серый | Правило не вычислялось (неподдерживаемый logsource, модификатор, агрегация…) |
| Красный восьмиугольник | Ошибка вычисления |
| Оранжевый треугольник | Есть замечания — например, лимит регулярного выражения |

Фильтр «Не вычислены / с замечаниями» собирает все такие правила. По встроенному набору сейчас
вычисляются 2734 правила, не поддерживаются 11 (шесть `file_access`, одно `file_rename`, три
с агрегацией `count()`, одно без condition), не загружаются 3 корреляционных файла Hayabusa.

### Лимит регулярных выражений

На одно значение поля регулярному выражению отводится 2 секунды процессорного времени.
Значения, не уложившиеся в лимит, считаются непроверенными, и к правилу добавляется замечание:
сколько значений не проверено и по какому полю.

## Экран «Детекты»

**Панель:** фильтр «Сработавшие / Все вычисленные / Не вычислены / с замечаниями / Все правила»,
минимальный уровень, поиск по названию, автору, тегу, пути или id, меню «Правила», запуск и
остановка прогона с прогрессом.

**Таблица:** Уровень, Правило, Событий, Хостов, Автор, Первое и последнее срабатывание, Набор,
Статус. Двойной клик — события правила. Контекстное меню: «События правила», «События правила в
таймлайне», «Скопировать DQL правила», «Скопировать запрос событий» (`rule = "<id>"`).

**Карточка правила:**

- название, уровень, статус, набор, автор, путь и id, даты создания и изменения;
- замечания и причины, если есть;
- «Сработало на N событиях, хостов: M», период, кнопки «События» и «В таймлайне»;
- описание;
- «Как проверялось»: logsource, варианты с переименованиями полей, итоговый DQL с кнопками
  «Выполнить этот DQL» и «Скопировать», время вычисления;
- теги — техники MITRE ATT&CK ссылками на attack.mitre.org;
- «Ложные срабатывания (по мнению автора)», ссылки из правила, исходный YAML.

**Подвал:** время прогона, сколько правил вычислено, не поддерживается, не загружено, с ошибками
и замечаниями, сколько сработало и на скольких событиях, длительность.

## Где ещё видны срабатывания

- В деталях события — блок «Сработавшие правила» с уровнем, названием, автором и набором.
  Клик открывает карточку правила.
- В боковой панели раздела «События» — уровни правил со счётчиками и ссылка «Все сработавшие
  правила…».
- В запросах — поля `rule` и `rulelevel`: `rule = "<id или название>"`, `rulelevel >= high`.
- Экспорт сработавших правил в CSV — см. [Экспорт](export-cli.html#экспорт-детектов).

## Проверка движка

Команда `evtxdump sigma <кейс> --pack rules.json --verify` перепроверяет каждое сработавшее правило
независимым упрощённым вычислителем, который читает исходное правило напрямую, и сообщает о
расхождениях в обе стороны. Это проверка самого движка, а не данных; в приложении её нет.
