## Принципы

- **Исходные данные только читаются.** Журналы открываются только на чтение и отображаются в память
  только для чтения. База кейса открывается приложением для чтения; писать в неё могут только
  закладки и результаты детектов, через отдельное подключение.
- **Ничего не скрывается.** Восстановленные записи, чанки за заголовком, ошибки контрольных сумм,
  эвристические связи, неподдерживаемые правила, лимиты и пропуски — всё помечено и объяснено в
  интерфейсе.
- **Запросы — не SQL.** Пользовательский текст никогда не становится SQL-запросом.

## Состав

| Модуль | Что делает |
|---|---|
| Приложение | SwiftUI и AppKit. Таблица событий — `NSTableView`: SwiftUI-таблица не остаётся плавной на миллионах строк |
| `EvtxCore` | Собственный парсер EVTX и BinXML на Swift, без внешних библиотек |
| `DaybookStore` | Импорт, хранилище кейса на SQLite, движок DQL, сущности, сеансы, процессы, экспорт |
| `DaybookSigma` | Разбор правил Sigma, перевод в DQL, прогон, проверка движка |
| `evtxdump` | Утилита командной строки на том же ядре |

Единственная внешняя зависимость — [Yams](https://github.com/jpsim/Yams) (MIT) для YAML правил Sigma.

## Парсер EVTX

- Файл отображается в память. Формат определяется по сигнатуре `ElfFile\0`, а не по расширению.
- Чанки по 64 КиБ независимы, поэтому разбираются параллельно на всех ядрах.
- Перебираются **все физические чанки**, а не только перечисленные в заголовке. В «живых» журналах
  счётчик чанков в заголовке устаревает, и самые свежие события лежат в чанках за ним.
- У каждого чанка проверяются CRC32 заголовка и данных. Ошибка не останавливает разбор, а
  помечает записи.
- Шаблоны BinXML разбираются один раз на чанк и кешируются; вложенный BinXML поддерживается.
- Поддерживаются все типы значений формата: строки, числа, GUID, SID, FILETIME, SYSTEMTIME,
  бинарные данные, массивы.
- Запись с ошибкой разбора не теряется: сохраняется всё прочитанное и ставится флаг.
- Slack-область чанков просматривается в поисках остатков старых записей (см.
  [Восстановление записей](cases-import.html#восстановление-записей-из-slack)).

## Импорт

1. Параллельный проход по всем чанкам: системные поля, время, место записи; попутно собирается
   библиотека шаблонов всех файлов.
2. Восстановление записей из slack с шаблонами всего кейса.
3. Сортировка по времени. События получают номера в порядке времени, поэтому любой список номеров
   уже упорядочен по времени. Одинаковые копии объединяются.
4. Повторный параллельный разбор и запись событий в базу группами по 256 чанков.
5. Индексы: posting-листы, индексы базы, полнотекстовый индекс, реестр сущностей.

## Хранилище кейса

- **Словарь строк.** Каждое уникальное значение или имя поля хранится один раз, вместе с хешем
  строки в нижнем регистре и числовым значением, если строка — число.
- **События.** Одна строка на событие: время, системные поля и упакованные пары «поле → значение».
  Таблица и детали показываются без соединений таблиц.
- **Posting-листы.** Для каждой пары «поле = значение» — отсортированный и сжатый список номеров
  событий. Системные свойства — те же пары с ключами `@EventID`, `@Channel` и т. д.
- **Полнотекстовый индекс** — триграммный FTS5 по словарю для поиска подстрок.
- **`ts.bin`** — время событий подряд; временное окно — двоичный поиск.
- **XML и сырые байты** не хранятся: при открытии деталей запись перечитывается из исходного файла
  по сохранённому месту (чанк и смещение). Номер записи сверяется, чтобы заметить изменённый файл.
  Исключение — записи с чужим или отсутствующим шаблоном: их XML сохраняется при импорте.

## Выполнение запросов

Запрос разбирается в дерево. Каждое условие превращается в множество номеров событий через словарь
и posting-листы; `and`, `or`, `not` — пересечение, объединение и разность отсортированных множеств.
Подробнее — в разделе [DQL](dql.html#как-выполняется-запрос).

## Детали события

Поля события берутся из кейса и появляются сразу. XML и байты записи читаются из исходного файла
отдельно, в фоновом потоке и без блокировки базы: медленный или недоступный файл не тормозит
интерфейс. Пока файл читается, вкладки XML и Hex показывают состояние: чтение, «файл не отвечает»
(дольше 3 секунд), «не найден», «нет доступа» или «файл изменился после импорта».

## Производительность

Замеры на Mac с Apple M5 Pro, тестовый набор — 108 журналов контроллера домена (906 МБ,
632 872 события):

| Операция | Время |
|---|---|
| Импорт | около 13 с |
| Типичные запросы | 1–380 мс |
| Все 2748 правил Sigma | около 8 с |
| Импорт 10 копий набора (6,4 млн событий) | 67 с, пик памяти 2,2 ГБ |
| Правила Sigma на 6,4 млн событий | 24,5 с |

## Ограничения

| Ограничение | Подробности |
|---|---|
| Число событий | Меньше 2³¹ в одном кейсе |
| Число файлов | Меньше 65 535 в одном кейсе |
| Память при импорте | Около 64 байт на запись плюс индекс «поле = значение» целиком в памяти до конца импорта |
| Формат `.evt` | Windows XP/2003 не поддерживается |
| Неполный последний чанк | Не разбирается, его размер показан в «Сведениях о кейсе» |
| CRC заголовка файла | Вычисляется, но пока не показывается |
| Описание события | Формируется при показе: по нему нельзя искать, в экспорт не попадает |
| EventRecordID, ProcessID, ThreadID | Видны в деталях и в экспорте, но в запросах пока недоступны |
| Новое место исходников | Указать новый путь к перемещённым журналам пока нельзя |
| Mac на Intel | Сборка не проверялась |
